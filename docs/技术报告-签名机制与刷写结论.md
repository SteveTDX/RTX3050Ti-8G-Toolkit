# 调研报告：Windows 下刷入自改 vBIOS / 绕过 Ampere 签名校验的可行性

> 对象：本机 RTX 3050 Ti Laptop（GA107 / 25A0，8GB 魔改），目标 ROM：`RTX3050Ti_HPPower_mod.rom`（80W/95W 移植版）
> 日期：2026-10-15 ｜ 方法：nvflash 二进制字符串取证 + 本机实测 + 社区一手资料交叉验证

---

## 一、结论（先行）

1. **自改（usermod）Ampere vBIOS 的软件刷写：当前不存在可行方法。** RTX 30 系起 NVIDIA 采用 BCRT 2.0 + **HMAC 证书**，改动任一字节即失效。本机实测：nvflash 5.867 与 nvflashk 均被 `CERT20_VDPA_SIG_INVALID` 拦截，且**在写入前失败**（"Nothing changed!"），显卡未受任何影响。
2. **唯一"不碰签名就能拿到 80W"的软件路线：交叉刷入官方已签名的 OEM ROM**（HP/ASUS/Dell/Alienware 210618，均为 Default 80W / Max 95W）。签名合法，可软件刷写；代价是 4GB SKU 显存配置（显存可能回退 4GB，需实测确认），且可随时刷回原厂 ROM 恢复 8GB。
3. **值得实测的新线索：nvflash 的 InfoROM 功耗策略对象**（`--addpp TGP`、`--addtgpapp`，单位 mW）。它写入 InfoROM 的 PTD 对象而非受签名的 VBIOS 区，代码路径明确打印 "Skipping VBIOS Verification / Devinit"——若本卡支持，可在**不刷 ROM** 的前提下调整 TGP。
4. **校验和不是瓶颈**：8bit/32bit 校验和即使修好也过不了 HMAC 证书。伪造签名需 NVIDIA 的 RSA3K 私钥 + HMAC 对称密钥，公开渠道无泄漏记录。

## 二、失败机制（为什么会报 Invalid firmware image）

**流程链**：nvflash → 向 GPU 的 Falcon/PMU 发送 `NV_UCODE_CMD_VBIOS_VERIFY` → uCode 校验 BCRT（BIOS Certificate 2.0）中 **VDPA**（VBIOS Data Protected Area）内各 Internal Block 的签名 → 返回 `NV_UCODE_ERR_CODE_CERT20_VDPA_SIG_INVALID` → 工具打印 "Nothing changed!"（**未写入任何数据**）。

**二进制取证证据**（从 nvflashb.exe / nvflashk.exe 提取）：

| 证据 | 含义 |
|---|---|
| `NV_UCODE_ERR_CODE_CERT20_VDPA_SIG_INVALID` | 本次失败的精确错误码，VDPA 区签名失效 |
| `BCRT_ERROR_CODE_CERT20_BIT_2_VDPA_TABLE_LOC_TYPE_UNEXPECTED` 等 | VDPA 是受保护的表格区（IntBlk 条目） |
| `FalconUcodeHulkProd` / `FalconUcodeHulkDbg` | Falcon 安全处理器产品/调试 uCode |
| `PROD_ALTSIG_PRESENT` / `DEBUG_ALTSIG_PRESENT` / `3AES Debug Signature` | 存在"生产签名"与"调试签名"两套体系 |
| `NV_UCODE_ERR_CODE_CMD_VBIOS_VERIFY_DEBUG_FUSE_BOARD` | 调试签名路径需 **debug fuse** 的工程卡 |
| `--dbgtokenrequest` / `--installtoken` / `--aggregatetoken` | 调试令牌申请流程（NVIDIA 内部/授权渠道） |
| `boot ucode SW rev is revoked`、`SPI access has been revoked` | 回滚与吊销机制 |

**社区一手佐证**（OMGVflash 作者 Veii，TechPowerUp 原帖）：
> "If the tool fails on your custom rom edit, It means you do not pass both verifications: the 8-bit Checksum's and the 32-bit File-checksum. **For RTX 3000-4000+, this includes the HMAC certificate.**"

## 三、工具全景与可行性

| 工具 / 路径 | 原理 | Ampere 自改 ROM | 状态 |
|---|---|---|---|
| nvflash 5.867（官方） | 全量校验 + Falcon 验签 | ❌ | **本机实测失败** |
| nvflashk prerelease (2023-08) | 强制开启 NVIDIA 内置的 mismatch bypass（`-6`），仅绕过板型/ID 检查 | ❌ | **本机实测失败**（ID 完全匹配仍报同一错误） |

## 四、可执行的替代路径（按推荐顺序）

### 路径 A｜交叉刷官方签名 80W ROM（最实用，签名天然合法）

```powershell
cd D:\tmp\workbuddy_space\2026-10-14-21-01-54\gpu_info
.\nvflashk.exe -6 HP.RTX3050TiMobile.4096.210618.rom
```

- 预期：功耗 Default 60W→**80W**、Max 60W→**95W**；显存**可能回退 4096 MiB**（4GB SKU 配置）
- 四个 OEM 功耗完全一致，刷哪个都一样；不满意可 `.\nvflashk.exe -6 RTX3050Ti_Laptop_94.07.3a.00.0e.rom` 刷回原厂（同样签名合法）
- 有核显兜底（Optimus），刷坏可救

### 路径 B｜InfoROM 功耗策略（新线索，测试成本为零）

二进制中提取到的官方帮助文本：

```
-- Help for --addpp/--delpp power policies descriptions --
    Policy         Description
    TGP            Total GPU Power
      firstWorkloadParam:  fixed point 20.12 (decimal)
      secondWorkloadParam: fixed point 20.12 (decimal)
  --addtgpapp SGEMM 60000 15000 900 500
  --delapp SGEMM
    Notes: for --addtgpapp argument format:
      fbRailPwrmW:         milliwatts (decimal)
      otherRailPwrmW:      milliwatts (decimal)
```

支持的负载 profile：SGEMM / HMMA / IMMA / TRANSFORMER / DMMA_PERF / DMMA_HIGH_K / DMMA_LOW_K / CUSTOMER_CUSTOM_0-7。

**关键**：这些命令的操作对象写在 **InfoROM**（`Updating PTD data in InfoROM image`、`InfoROM PTD data updated successfully`），同区还含 `Skipping VBIOS Verification / Devinit`——即**不触发 VBIOS 验签**，因此不被签名失败阻断。

待验证命令（管理员终端）：

```powershell
.\nvflashb.exe --help pp          # 查看功耗策略完整语法
.\nvflashb.exe --help app         # 查看 app profile 语法
.\nvflashb.exe --listpp           # 列出当前功耗策略
.\nvflashb.exe --listapp          # 列出当前 TGP app profile
```

> **限制提示**：该特性面向按负载功耗封顶（GEMM/Transformer 等计算负载），主要服务于数据中心产品；GeForce 笔记本 GPU 大概率返回"不支持"。但确认只需 4 条只读命令，若支持则是最优解（不改 VBIOS、不刷写、可逆）。

### 路径 C｜诊断实验：确认本机当前 8GB ROM 是否通过验签

```powershell
.\nvflashk.exe -6 RTX3050Ti_Laptop_94.07.3a.00.0e.rom
```

- 内容与原片完全相同，最坏情况只是重写相同数据，**无风险**
- 结果判读：
  - 若报 `Invalid firmware image detected` → 当前 8GB ROM 本身**未签名**，说明本卡**不在启动期强制验签**（否则当年魔改不可能开机）→ 那么用编程器写入 HPPower_mod **可以正常开机**
  - 若通过并继续 → 当前 ROM 是官方签名版（8GB 来自官方 8GB SKU 固件）

### 路径 D｜不刷固件的其他方案

| 方案 | 可行性 | 说明 |
|---|---|---|
| `nvidia-smi -pl` / Afterburner 功耗滑条 | ❌ 已实测锁定 60W | VBIOS 内 Max Power Limit 就是 60W |
| EC / Dynamic Boost 调整 | ❌ 用户不可设置 | 由 OEM EC 固件与驱动协商 |
| **Shunt mod（电流采样电阻并联）** | ⚠️ 硬件可行 | 改电流采样使 GPU"测到"的功耗偏低，从而允许更高实际功耗；**无需编程器、无需刷 ROM**，但需焊接、有风险、精度靠计算 |
| **CH341A + SOP-8 免拆夹（免拆芯片）** | ⚠️ 折中 | 不拆芯片、不焊，夹住 IS25WP016D 在线写入；笔记本板上 3.3V 可能干扰，成功率低于拆焊 |
| 编程器拆焊写入 | ✅ 唯一确定方案 | 若路径 C 证实启动期不验签，则此法可得到 80W + 8GB |

## 六、实测闭环（2026-10-15 下午，最终结论）

在 nvflash 官方二进制上制作了两代补丁并做了 4 组对照实验（脚本 `re_patch_nvflash.py`，补丁版 `nvflashb_nosig.exe` / `nvflashb_nosig2.exe`）：

| # | 工具 | 目标镜像 | 镜像签名 | 验签调用 | EWR（真实写入）结果 |
|---|---|---|---|---|---|
| 1 | nvflashk | HPPower_mod | 无效 | 执行 | `Invalid firmware image detected`（未写入） |
| 2 | nvflashb_nosig（v1） | HPPower_mod | 无效 | 执行但失败 | `Falcon In HALT or STOP state`（未写入） |
| 3 | nvflashb_nosig（v1） | 原厂同内容 | 有效 | 执行成功 | 成功（`Update successful`，Exit Code 0） |
| 4 | nvflashb_nosig2（v2，跳过验签调用） | 原厂同内容 | **有效** | **跳过** | `NV_UCODE_ERR_CODE_CMD_EWR_OK_TO_FLASH_CHECK_FAILED`（0x6C） |
| 5 | nvflashb_nosig2（v2） | HPPower_mod | 无效 | 跳过 | 同上 0x6C（证明非"空操作拒绝"） |

### 关键推论

- **第 3 组证明**：本机 EEPROM 写入通路完好——写保护已可由 `--protectoff` 解除，EWR 能完成全部页编程并回读校验通过（`stepC.log` 第 290 行 `Update successful`）。**阻塞点不是硬件写保护。**
- **第 4 组是决定性证据**：v2 跳过了验签调用后，**即使镜像本身签名完全合法（原厂 ROM），EWR 仍被 "OK to flash" 检查拒绝**。说明该检查并非只看镜像字节，而是依赖 GPU 侧由验签命令建立的授权状态。
- **合并结论**：GPU 只允许"通过验签的镜像"进入 EWR 写入流程。验签发生在显卡固件内部（PMU/Falcon uCode），其判定结果无法由主机侧伪造或绕过——**任何 nvflash 变体（包括 v1/v2 补丁）都不可能写入未签名镜像**。至此，签名校验机制在 Ampere 上的完整封锁链闭合。

### 修订后的最终路线

| 路线 | 状态 | 说明 |
|---|---|---|
| 主机侧绕过（nvflash 补丁） | ❌ **已实验证伪** | 4 组对照实验闭环，结论确定 |
| 交叉刷官方签名 OEM ROM | ✅ **可立即执行** | 通路已验证可用；Default 80W / Max 95W；显存是否回退 4GB 需实测；可随时刷回原厂 ROM |
| OMGVflash（Falcon 侧绕过） | ⚠️ 待获取 | omgvflash.com 本机不可达，仅 TechPowerUp 论坛附件（需账号）；作者称 3000+ 仍需 HMAC 证书，成功率存疑 |
| SPI 编程器写自改 ROM | ✅ 唯一确定获得 80W+8GB | 不受签名约束（Boot 阶段由本机实证可运行非标固件） |
| Shunt mod | ⚠️ 硬件替代 | 无需刷固件即可提升实际功耗上限 |

## 五、推荐执行顺序

1. **零风险信息收集**（路径 B 的 4 条只读命令 + 路径 C 的诊断刷写）
2. 若 B 支持 → 直接用 `--addpp TGP` 调整（最优，不动 VBIOS）
3. 否则 → **路径 A** 交叉刷 HP ROM 拿 80W，实测显存：若仍是 8192 MiB 则双赢；若回退 4GB 且不可接受 → 刷回原厂 ROM
4. 若必须 80W + 8GB 且不接受硬件操作 → 目前无解；可接受硬件 → 免拆夹或 shunt mod

## 附：本次调研的方法与产出

- 二进制取证脚本思路：提取 nvflashb.exe / nvflashk.exe 中所有 ≥6 字节可打印串，按 `cert / sign / sig / bypass / verif / ucode / override / HMAC / HULK / VDPA` 等关键字聚类，并重建 `--addpp`/`--addtgpapp` 帮助原文段（位于 `0x11E5348` 附近）
- 校验和实测：本机 raw 与 HPPower_mod raw 的整图 8bit 和分别为 `0x07` / `0x66`，而官方 HP/Dell 剥离容器后为 `0x5D` / `0x01`——**官方 ROM 的整图字节和也不为 0**，说明 NVIDIA 的校验和不是简单的"整图求和为 0"，校验和字段位置需专门逆向；即便修正，HMAC 证书仍是硬约束
